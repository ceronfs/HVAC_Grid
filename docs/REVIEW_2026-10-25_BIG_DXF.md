# 검토 — 큰 DXF가 HVAC Grid ①에서 잘 열리지 않음 (2026-10-25)

대상: HVAC Grid ① 도면·격실 **DXF 열기** → BOX 사본 `vendor/BOX_CAL_Enhance.html`(`VERSIONS.json` sha256_16 `8892c20e503108f2`) · 증상(사용자): 수십 MB DXF가 잘 열리지 않음 · 질문: 너무 복잡한 로직이 아닌가

## 강제 항목

| 항목 | 결과 |
|---|---|
| F-1 풍량은 여름 기준 하나 | 지킴 — 이 검토는 DXF 읽기만 다루고 풍량 코드를 건드리지 않음 |
| F-2 표준 값은 원문으로 | 지킴 — 표준 값을 인용하지 않음 |

## 결론

복잡한 것도 맞지만, 실제로 막히는 원인은 **계산량이 도면 크기의 제곱으로 느는 알고리즘 하나**와 **크기 한도 두 개**입니다. 그래서 수십 MB는 물론 **2 MB(선 약 2만 개)에서 이미 실 목록이 나오지 않습니다.** 1 MB에서도 실 목록을 한 번 구하는 데 15초가 걸리고, BOX는 이 목록을 화면·표·시트에서 여러 번 부릅니다.

### 최적화 평가

| 단계 | 평가 | 근거 |
|---|---|---|
| 파일 읽기·문자 코드 | 양호 | `arrayBuffer` + `TextDecoder` 한 번, 머리글 64 KB만 보고 코드 페이지 판단 |
| 분석(Worker) | 양호 | 본 화면을 막지 않고 Worker에서 분석, 취소·순서 검사 있음 |
| 본 화면 반영(`parseDXF`) | 미흡 | 결과 전체 복사, 원본 문자열을 상태에 보관, 레이어 정리 L×N, 동기 실행 |
| 실 찾기(`rooms` → `wallPanelAnalysis`) | **불량 — 병목** | 같은 방향 선 전부 짝짓기(N²), 짝마다 문자열 `Set`; 2 MB에서 멈춤 |
| 큰 파일 처리(16 MiB 이상) | **불량** | 대용량 엔진이 Deck·격실을 만들지 않아 HVAC Grid에 이어지지 않음 |
| 저장·복구 | 미흡 | 노드 500만 개 한도, 원본 DXF가 프로젝트에 들어감 |
| HVAC Grid 셸 | 미흡 | 크기 안내·실패 표시 없음, `→ BOX`만 알림 |

종합: 도면 크기 기준으로 **약 1 MB까지만 실용적**입니다. 수십 MB 일반배치도를 바로 열 수 있는 구조가 아닙니다.

| # | 수준 | 위치 | 내용 |
|---|---|---|---|
| 1 | P1 | BOX `wallPanelAnalysis` (사본 11380행대, `checked.add(pairKey)` 11406행) | 벽 패널(선 두 줄) 찾기가 방향이 같은 선을 **모두 서로 짝지어** 봅니다(`angleBucket` ±1). 일반배치도는 선이 거의 가로·세로 두 방향뿐이라 선 N개면 짝이 약 N²/4개입니다. 짝마다 `"id|id"` 문자열을 만들어 `Set`에 넣어서, 선 5만 5천 개(5 MB)면 `Set` 최대 크기(약 1,670만)를 넘어 **"Set maximum size exceeded"**로 15초 만에 멈춥니다. `rooms()`가 이 함수를 부르므로 실이 하나도 안 나옵니다. 가구·문·해치 선처럼 벽이 아닌 선도 모두 들어갑니다 |
| 2 | P1 | BOX `BOX_IMPORT_ROUTING.shouldUseStreamingImport` (16 MiB) | **16 MiB(약 16.8 MB) 이상**인 DXF는 일반 경로가 아니라 "대용량 엔진(ROOM/3D 시험 기능)"으로 갑니다. 이 엔진은 BOX의 Deck·격실을 만들지 않으므로 HVAC Grid ①에는 아무것도 생기지 않습니다. 셸은 `파일 → BOX`라고만 알리고 실패를 보여 주지 않습니다(`app/shell.js:511`) |
| 3 | P1 | BOX 프로젝트 `clone` (노드 500만 개 한도) | 15 MB 도면(객체 16만 개)에서 **"프로젝트 구조가 너무 큽니다."** 경고가 뜹니다. 모든 객체가 프로젝트 상태로 들어가고, 원본 DXF 문자열 전체도 `st.persistencePassthrough.dxfImports[].rawDxf`에 함께 저장됩니다(`parseDXF`, 사본 15771행) |
| 4 | P2 | BOX `parseDXF` | 거부된 객체가 하나라도 있으면 가져오기 전체를 중단합니다(`INCOMPLETE_DXF`). 큰 실제 도면일수록 걸리기 쉽습니다 |
| 5 | P2 | BOX `parseDXF` 마무리 | Worker가 분석한 결과를 본 화면에서 다시 통째로 복사하고(`copy(report.entities)`), 레이어 정리(레이어마다 전체 객체 검사), 벽 패널 분석, 화면 맞춤을 한 번에 동기로 실행합니다. 5 MB에 21초, 메모리 2 GB |
| 6 | P3 | 구조 | DXF 열기 단추 하나에 처리기가 세 겹입니다(옛 처리기 → L4 Worker 배치 → 대용량 엔진이 `onchange`를 덮어씀). 크기 하나로 길이 갈리고, 어느 길로 갔는지 사용자에게 보이지 않습니다 |

## 결정과 반영 (2026-10-25)

사용자 결정: **도면 정리는 SketchCAD에서 한 뒤 HVAC Grid에 넣는다.** 100 MB 이상 도면도 이 길로 처리한다. BOX 원본(A~C)은 이번에 고치지 않는다.

| 반영 | 내용 | 확인 |
|---|---|---|
| D. HVAC Grid 셸 `openBoxDxf` (`app/shell.js`) | 2 MB 이상이면 SketchCAD 경로를 안내하고 "그래도 열기"를 고르게 함, 16 MiB 이상이면 열지 않고 안내, 연 뒤에는 BOX 상태 줄(성공·실패)을 셸 상태 줄에 보여 줌 | `test/e2e/sketchcad.e2e.cjs` "DXF 열기 단추" |
| SketchCAD 실 자동 찾기 (`perf/big-drawings`) | 문자마다 도면 전체를 다시 훑어 실 목록을 만들던 것(`roomAt` → `roomEnts`, 문자 수 × 객체 수)을 한 번만 만들게 하고, 면적표(`roomData`)의 벽·구멍·문자 목록도 실마다가 아니라 한 번만 만듦 | 100 MB 141 s → 0.4 s, 150 MB 297 s → 1.7 s; 고치기 전·후 `roomData`·`findRoomsByText` 결과가 도면 6개에서 같음 |

200 MB(객체 226만): SketchCAD 열기 15.4 s → 정리 10.7 s → 실 자동 찾기 3.3 s → 실 만들기 4.6 s → 내보내기 1.8 s(21 KB) → HVAC Grid ① 29실. SketchCAD 메모리 2.8 GB. 250 MB는 10분 안에 끝나지 않아 사용자 지시로 중단했고, 확인 범위는 200 MB까지입니다.

### SketchCAD 계산용으로 열기 (`perf/calc-open`, `8295e36`)

사용자 지시 "일단 DXF 기준으로 효율화 수행하고 dwg는 나중에 결정하자"에 따른 두 번째 수정이다.

- 원인(20 MB 프로파일): 일반배치도 객체의 97%는 가구·해치·치수다. SketchCAD는 이것들을 모두 객체로 만들고, 실행 취소용 JSON 사본과 공간 색인까지 붙인 뒤, 계산용 정리에서 버렸다. 정리(숨기기)는 옮긴 객체의 바뀌기 전 JSON을 실행 취소 기록에 따로 남긴다(20 MB에 34 MB 문자).
- 수정: 16 MB 이상 DXF는 해석한 뒤 레이어 선택 창을 띄운다. 처음 선택 상태는 계산용 정리와 같은 규칙(`calcKeepLayers`, 두 곳이 같은 함수를 쓴다)으로 정하고, 문자는 모두 읽고, 해치·치수는 뺀다. 고르지 않은 객체는 만들지 않는다.
- 같은 결과: 20 MB에서 계산용으로 열기 = 전체 열기 + 계산용 정리(삭제, 기본값). 객체·블록·쓰는 레이어·실 자동 찾기·면적표(29실)가 같고, SketchCAD 빈 기본 레이어(CENTER·HIDDEN·TEXT)만 남는다. 내보낸 HVAC Grid용 DXF의 실 번호·이름·면적도 같다. 16 MB 미만은 선택 창이 없고 결과가 고치기 전과 같다(5개 파일). `test/e2e/sketchcad.e2e.cjs`도 통과한다.
- 효과: 100 MB에서 열기 → 면적표가 약 15 s → 3.6 s, 정리 후 메모리 1 GB 이상 → 22 MB, 가장 긴 멈춤 4.1 s → 1.8 s. 해석하는 동안의 최대 메모리 741 MB가 이제 상한을 정한다(줄 배열·코드 쌍 배열). 200 MB는 지시에 따라 다시 재지 않았다.

## DWG로 바로 넣으면 더 효율적인가 (추가 측정 없이 평가)

| 관점 | 평가 | 근거 |
|---|---|---|
| 처리 속도 | 이득 작음 | 200 MB 전 과정 36 s 중 파일을 읽어 객체로 만드는 "열기"가 15.4 s. DWG는 이 중 문자 해석 부분만 줄이고, 객체 수(226만)는 같으므로 정리·실 찾기·메모리(2.8 GB, 대부분 객체)는 그대로 |
| 파일 크기 | 이득 | DWG는 압축된 이진 형식이라 같은 도면의 ASCII DXF보다 보통 훨씬 작음(이번에 재지 않음) |
| 작업 흐름 | 이득 | 받은 DWG를 CAD에서 DXF로 바꾸는 단계가 없어짐 — 실제로 가장 큰 효과 |
| 있는 엔진 | 쓸 수 있으나 검증 부족 | PHG에 LibreDWG(libredwg-web 0.7.14, R13~2018) 직접 해독기가 있음(`PHG/PHG_DWG_Integration`, `PHG_Rust_DWG v0.4`). 배경 표시용이고, 실제 DWG는 0.58 MB까지만 검증, 100 MB는 미검증. REGION·일부 치수 등 미반영 객체가 남고 해독 중 메모리가 파일보다 큼 |
| 라이선스 | 결정 필요 | LibreDWG는 GPL-3.0 — SketchCAD에 넣으면 배포하는 HTML도 GPL-3.0(소스 공개) |

결론: 속도·메모리만 보면 DWG 입력의 이득은 작고, 효과는 **DXF 변환 단계를 없애는 것**입니다. 넣는다면 HVAC Grid가 아니라 **SketchCAD의 입력**으로 넣는 것이 맞습니다(HVAC Grid는 SketchCAD가 내보낸 작은 DXF만 받음). 그 전에 GPL-3.0 배포 조건을 정해야 합니다.

측정 스크립트는 이번 세션 임시 폴더에 있습니다(합성 도면 생성 + 크기별 측정, 오류 스택 확인).
